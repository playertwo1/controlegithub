# C21.2 — Pesquisa oficial sobre download e instalação de APK

Consulta em 20/10/2026. Fontes primárias: documentação Android/GitHub e código AOSP. O contrato vigente é [C21.2](../../plan/contracts/C21.2.md); este registro reúne evidência técnica, e o contrato define a implementação escolhida.

Decisão adotada no contrato: streaming em `CoroutineWorker`, validação do SHA-256 antes da publicação, `MediaStore` em API 29+ e SAF em API 26–28, instalação manual por `ACTION_VIEW` com URI `content://`. A recomendação abaixo de `PackageInstaller.Session` é uma alternativa técnica e não faz parte deste escopo.

## Achados

### DownloadManager

- `DownloadManager.Request` aceita headers HTTP arbitrários, permite gravar na pasta pública Downloads e configura notificação durante o download e após concluir. Para `targetSdk` Q ou superior, `setDestinationInExternalPublicDir(DIRECTORY_DOWNLOADS, ...)` não exige `WRITE_EXTERNAL_STORAGE`; evite `setDestinationUri(file://...)`, cujas exigências diferem. [Headers da requisição](https://developer.android.com/reference/android/app/DownloadManager.Request#addRequestHeader(java.lang.String,java.lang.String)), [destino público](https://developer.android.com/reference/android/app/DownloadManager.Request#setDestinationInExternalPublicDir(java.lang.String,java.lang.String)), [notificação](https://developer.android.com/reference/android/app/DownloadManager.Request#setNotificationVisibility(int))
- `setDestinationInExternalPublicDir` existe desde API 9, portanto cobre `minSdk 26`. `MediaStore.Downloads` só existe desde API 29. Em API 26–28, `ACTION_CREATE_DOCUMENT` (API 19+) é a saída sem permissão ampla: o seletor do sistema deixa o usuário escolher provedor/local e retorna uma URI `content://`; o Android inclui o provedor Downloads e o usuário controla a escolha. Se o requisito exigir salvar automaticamente numa pasta pública fixa também em API 26–28, isso implica uma decisão adicional de permissão/acesso legado. [DownloadManager destino e regra de permissão](https://developer.android.com/reference/android/app/DownloadManager.Request#setDestinationInExternalPublicDir(java.lang.String,java.lang.String)), [MediaStore Downloads desde API 29](https://developer.android.com/reference/android/provider/MediaStore.Downloads), [guia SAF e provedores integrados](https://developer.android.com/guide/topics/providers/document-provider), [ACTION_CREATE_DOCUMENT](https://developer.android.com/reference/android/content/Intent#ACTION_CREATE_DOCUMENT)
- O progresso pode ser consultado por `COLUMN_BYTES_DOWNLOADED_SO_FAR` e `COLUMN_TOTAL_SIZE_BYTES`; o tamanho total começa em `-1`, então a interface precisa admitir progresso indeterminado. `COLUMN_REASON` distingue HTTP e falhas locais, inclusive espaço insuficiente e arquivo existente. `remove(id)` cancela e apaga o arquivo parcial ou concluído; `getUriForDownloadedFile(id)` fornece a URI de um download concluído. [DownloadManager API](https://developer.android.com/reference/android/app/DownloadManager)
- **Risco de credencial:** o código AOSP do Android 17 abre cada URL do ciclo de redirects, reaplica os headers customizados e então processa a resposta 3xx, atualizando a URL para o próximo ciclo. Assim, adicionar `Authorization: Bearer …` ao `DownloadManager.Request` pode reenviar o token ao host indicado pelo `Location`. [AOSP Android 17 `DownloadThread`](https://android.googlesource.com/platform/packages/providers/DownloadProvider/+/refs/tags/android-17.0.0_r1/src/com/android/providers/downloads/DownloadThread.java#L445-L519). A API pública do `DownloadManager` documenta a inclusão de headers, mas não promete removê-los em redirects.

### GitHub REST para assets

- `GET /repos/{owner}/{repo}/releases/assets/{asset_id}` com `Accept: application/octet-stream` pode responder `200` com o corpo binário ou `302` para a localização do arquivo; a documentação exige tratar ambos. Para repositório privado, fine-grained token precisa de permissão `Contents: read`. [GitHub REST: Get a release asset](https://docs.github.com/en/rest/releases/assets#get-a-release-asset)
- O exemplo JSON de metadados do asset inclui `digest` no formato `sha256:<hex>`. Como o `200` com `application/octet-stream` é o corpo binário, obtenha os metadados separadamente (ou reutilize-os da listagem da release) antes de comparar esse digest. Releases sem campo `digest` exigem fallback; um `SHA256SUMS.txt` publicado junto na mesma release não autentica o APK contra quem controla essa release. [Exemplo JSON oficial](https://docs.github.com/en/rest/releases/assets#get-a-release-asset--response)
- Neste projeto, [GitHubHttpClient](../../app/src/main/java/com/playertwo/controlegithub/GitHubHttpClient.kt) desativa redirects e asserta isso em [GitHubHttpClientTest](../../app/src/test/java/com/playertwo/controlegithub/GitHubHttpClientTest.kt). [GitHubActionJobLogs](../../app/src/main/java/com/playertwo/controlegithub/GitHubActionJobLogs.kt) já trata separadamente o redirect assinado sem enviar o bearer; [GitHubActionJobLogsTest](../../app/src/test/java/com/playertwo/controlegithub/GitHubActionJobLogsTest.kt) verifica a ausência de `Authorization` na segunda requisição. Esse é o precedente local para assets privados.
- A implementação atual não serve para o corpo binário sem ajuste: `GitHubHttpClient` fixa `Accept: application/vnd.github+json` e transforma qualquer resposta 2xx em `String` via UTF-8 (`GitHubHttpClient.kt`, linhas 178 e 213). O `200` de asset exige um caminho de streaming em bytes; não leia o APK inteiro como texto nem mantenha todo o binário na memória. [Código local](../../app/src/main/java/com/playertwo/controlegithub/GitHubHttpClient.kt)

### Abrir o instalador Android

- Para compartilhar um arquivo privado com outro app, Android exige URI `content://` e concessão temporária `FLAG_GRANT_READ_URI_PERMISSION`; `FileProvider` deve ser não exportado e com escopo de diretório limitado. URI `file://` não é adequada. [FileProvider setup](https://developer.android.com/training/secure-file-sharing/setup-sharing) e [permissão temporária](https://developer.android.com/training/secure-file-sharing/share-file#grant-permissions-for-the-file)
- `Intent.ACTION_INSTALL_PACKAGE` foi descontinuado no API 29; a referência Android indica `PackageInstaller`. Uma `PackageInstaller.Session` recebe o APK via `openWrite()` e `commit()` pode exigir ação do usuário, cujo resultado deve ser tratado. `setRequireUserAction(USER_ACTION_REQUIRED)` explicita o fluxo manual a partir do API 31; em qualquer versão, o app deve estar preparado para a confirmação/status pendente do sistema. [Intent](https://developer.android.com/reference/android/content/Intent#ACTION_INSTALL_PACKAGE), [Session](https://developer.android.com/reference/android/content/pm/PackageInstaller.Session#commit(android.content.IntentSender)) e [SessionParams](https://developer.android.com/reference/android/content/pm/PackageInstaller.SessionParams#setRequireUserAction(int))
- A partir do Android 8, o usuário controla quais fontes podem solicitar instalações. Com `REQUEST_INSTALL_PACKAGES` declarado, consulte `PackageManager.canRequestPackageInstalls()`; se retornar falso, encaminhe para `Settings.ACTION_MANAGE_UNKNOWN_APP_SOURCES` com o pacote e reavalie a permissão ao voltar. [PackageManager](https://developer.android.com/reference/android/content/pm/PackageManager#canRequestPackageInstalls()), [Settings](https://developer.android.com/reference/android/provider/Settings#ACTION_MANAGE_UNKNOWN_APP_SOURCES), [Manifest permission](https://developer.android.com/reference/android/Manifest.permission#REQUEST_INSTALL_PACKAGES)
- Se a distribuição for pelo Google Play, `REQUEST_INSTALL_PACKAGES` é restrita a apps cuja função principal envolva receber/enviar pacotes e habilitar instalação iniciada pelo usuário; não pode servir para autoatualização. O produto atual é um cliente GitHub, então a elegibilidade não está estabelecida por este contrato. Resolver o canal de distribuição antes de adicionar a permissão ao manifesto. [Política Google Play](https://support.google.com/googleplay/android-developer/answer/16558241)

### Trabalho em segundo plano

- `WorkManager` suporta workers longos por meio de foreground service/notificação configurável; `CoroutineWorker.setForeground()` e `createCancelPendingIntent()` permitem notificar progresso e oferecer cancelamento. `setProgress()` e `WorkInfo` fornecem progresso intermediário observável enquanto o worker está rodando. [Workers longos/notificação/cancelamento](https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/long-running), [progresso](https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/observe)
- Limite atual relevante: desde Android 16, workers longos do WorkManager ainda usam `JobScheduler` e podem consumir a cota de jobs do app; a documentação sugere considerar User-Initiated Data Transfer Job quando o download responde a uma ação do usuário. Isso não invalida WorkManager como baseline, mas exige validar o comportamento Android 16+ e não prometer execução irrestrita. [Limite Android 16 e alternativa](https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/long-running)

## Recomendação para fechar o contrato mínimo

1. **Usar uma única transferência em streaming controlada pelo app; não enviar bearer via `DownloadManager`.** Requisitar apenas o endpoint asset esperado com `Accept: application/octet-stream` e bearer. Com `200`, copiar o corpo em bytes; com `302`, aceitar no máximo o redirect esperado, exigir `Location` HTTPS e abrir a URL sem `Authorization`; falhar em status/redirects fora desse fluxo. A Location é temporária e não deve aparecer em log, UI ou notificação. O AOSP pode repetir os headers do `DownloadManager` ao redirecionar, então o risco persiste mesmo que o primeiro host seja GitHub. [Contrato GitHub dos dois status](https://docs.github.com/en/rest/releases/assets#get-a-release-asset), [ciclo de headers AOSP Android 17](https://android.googlesource.com/platform/packages/providers/DownloadProvider/+/refs/tags/android-17.0.0_r1/src/com/android/providers/downloads/DownloadThread.java#L445-L519)
2. Rodar essa transferência num `CoroutineWorker` longo com foreground notification, progresso por bytes e cancelamento ligado ao worker. Se o total não for conhecido, exibir progresso indeterminado. Guardar o arquivo em área privada temporária até validar o corpo e o digest disponível; apagar o parcial em cancelamento/falha. O app atual lê respostas 2xx de `GitHubHttpClient` como UTF-8 `String`; será necessário um caminho streaming binário e redirects explicitamente controlados. [WorkManager foreground](https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/long-running), [progresso observável](https://developer.android.com/develop/background-work/background-tasks/persistent/how-to/observe), [progresso no DownloadManager](https://developer.android.com/reference/android/app/DownloadManager#COLUMN_TOTAL_SIZE_BYTES)
3. Publicar o APK validado na pasta Downloads depois do download: em API 29+ inserir em `MediaStore.Downloads` e manter `IS_PENDING` durante a cópia/publicar após terminar; em API 26–28 usar `ACTION_CREATE_DOCUMENT` e permitir que o usuário escolha Downloads no seletor SAF. Isso evita `WRITE_EXTERNAL_STORAGE` ampla e a exposição de arquivo parcial, porém a seleção manual em API 26–28 é uma diferença de UX a registrar no contrato. Se for obrigatório salvar automaticamente em `Downloads` fixa nessa faixa, essa exigência precisa escolher e aprovar explicitamente um caminho legado. [Downloads/escopo por app](https://developer.android.com/training/data-storage/shared/media#downloads), [IS_PENDING](https://developer.android.com/reference/android/provider/MediaStore.MediaColumns#IS_PENDING), [SAF sem permissão ampla e picker](https://developer.android.com/training/data-storage/shared/documents-files)
4. Manter no contrato os estados: queued/running (bytes e percentual apenas quando total conhecido), concluído, cancelado, falta de espaço, HTTP/autorização e conflito de nome. Não sobrescrever silenciosamente arquivo do usuário. Na gravação para Downloads, usar nome sem colisão; em cancelamento/falha remover staging e item MediaStore pendente, ou não publicar o documento SAF incompleto.
5. Preferir instalar da cópia privada validada usando `PackageInstaller.Session.openWrite()` e `commit()`, sem FileProvider: abrir a instalação consome stream local do próprio app. A sessão pode exigir ação do usuário e devolver `STATUS_PENDING_USER_ACTION`; reportar instalado somente após status de sucesso. Se optar por instalar de arquivo privado via intent externo, aí sim precisa `content://`, grant temporário e `FileProvider` restrito. [PackageInstaller stream e commit](https://developer.android.com/reference/android/content/pm/PackageInstaller.Session), [URI permissions](https://developer.android.com/training/secure-file-sharing/share-file#grant-permissions-for-the-file)
6. Restringir o aceite inicial a um APK monolítico compatível. Se incluir APK dividido, uma sessão deve receber o APK base e splits selecionados com mesmo pacote, versão e assinatura; isso amplia escopo e não é equivalente a um único `.apk`. Exibir “SHA-256 confere” como comparação de integridade com a fonte escolhida, não como assinatura/autenticidade: um `SHA256SUMS.txt` publicado junto do APK pode ser substituído na mesma release. Preferir o `digest` dos metadados da API quando presente e manter fallback explícito quando ausente. [PackageInstaller e constraints de splits](https://developer.android.com/reference/android/content/pm/PackageInstaller), [exemplo de digest](https://docs.github.com/en/rest/releases/assets#get-a-release-asset--response)

## Limites desta pesquisa

O projeto declara `minSdk 26` e `targetSdk 36` ([app/build.gradle.kts](../../app/build.gradle.kts)). A recomendação segura assume que a seleção via SAF em API 26–28 é aceitável para salvar o APK em local escolhido pelo usuário; se a exigência for pasta Downloads fixa sem picker, a compatibilidade exige decisão explícita sobre acesso legado. A pesquisa não confirmou o canal final de distribuição nem os hosts reais do redirect de asset para contas/releases privadas. Antes de implementação, fixar limite de redirect/HTTPS e provar os casos fixtures `200` e `302` sem token real em logs; validar também comportamento WorkManager em Android 16+.
