# C13.2 — Enviar revisão de PR

## Escopo

Permitir que o usuário envie uma revisão formal (Pull Request Review) na tela de detalhe do Pull Request (`GitHubPullRequestDetailScreen`), utilizando a rota REST autenticada `POST /repos/{owner}/{repo}/pulls/{pull_number}/reviews` da API do GitHub.

Comportamentos incluídos:
- Formulário para submissão de revisão formal com seleção de parecer:
  - "Aprovar" (`APPROVE`)
  - "Solicitar alterações" (`REQUEST_CHANGES`)
  - "Comentar revisão" (`COMMENT`)
- Campo de texto para o parecer da revisão.
- Validação local obrigatória quando "Solicitar alterações" for selecionado (corpo não pode estar vazio/em branco).
- Detecção e tratamento amigável de auto-revisão: autor do PR não pode aprovar ou solicitar alterações em seu próprio PR (retorno `422 Unprocessable Entity` mapeado para mensagem clara, além de aviso preventivo se `session.user.login == pullRequest.author`).
- Proteção anti-duplo clique (anti-double-tap) com desativação síncrona imediata do botão e exibição de indicador de progresso.
- Preservação integral do rascunho em caso de falha de conexão, timeout, `403 Forbidden`, `422 Unprocessable Entity` ou erro de servidor.
- Bloqueio imediato em modo offline (`isOffline = true`) com aviso informativo (sem fila oculta de mutações).
- Atualização imediata da lista de reviews na tela com o novo review adicionado após `200 OK`.

Exclusões deste contrato:
- Merge ou fechamento do Pull Request (fora da versão 1.0 conforme ROADMAP).
- Comentários em linhas específicas de diff de arquivos individuais (`/pulls/{number}/comments`).
- Edição ou cancelamento de revisões já submetidas.
- Fila de escrita offline para sincronização tardia (proibida pelas regras de segurança do projeto).

## Pré-condições e decisões

- Pré-requisito C13.1 (Comentar PR) concluído com sucesso (`DONE`).
- Acesso à API do GitHub:
  - Rota de revisão: `POST /repos/{owner}/{repo}/pulls/{pull_number}/reviews`.
  - Body: JSON com campos:
    - `event`: string obrigatória (`"APPROVE"`, `"REQUEST_CHANGES"`, ou `"COMMENT"`).
    - `body`: string opcional (obrigatória para `REQUEST_CHANGES`).
    - `commit_id`: SHA do commit head (`pullRequest.headSha`) para garantir que a revisão se aplica ao estado visualizado.
  - Status de sucesso: `200 OK` (retornando o objeto do review com `id`, `user`, `state`, `body`, `submitted_at`).
  - Respostas de erro esperadas:
    - `401 Unauthorized`: Sessão expirada ou revogada.
    - `403 Forbidden`: Usuário sem permissão de escrita ou revisão bloqueada.
    - `422 Unprocessable Entity`: Autor tentando aprovar seu próprio PR ou validação rejeitada pelo GitHub.
- Decisão sobre transporte HTTP (`GitHubHttpClient.kt`):
  - Utiliza o método `post(path, accessToken, jsonBody)` com streaming UTF-8 (`setFixedLengthStreamingMode`).
  - Sanitização via `escapeJson` puro Kotlin sem dependências externas.
- Decisão sobre UI:
  - Seção "Reviews" exibe botão/formulário "Nova revisão" com seletor de parecer, campo de parecer e botão "Enviar revisão".
  - UI 100% em português brasileiro.

## Aceite

1. **REVIEW-APPROVE (Aprovação de Pull Request com sucesso):**
   **Dado** um usuário autenticado na tela de detalhe de um PR de terceiros,
   **quando** seleciona "Aprovar" com ou sem texto de parecer e envia a revisão, e o servidor responde `200 OK`,
   **então** a nova revisão com estado "Aprovou" é adicionada à lista visível de reviews e o campo de texto é limpo.

2. **REVIEW-CHANGES (Solicitação de alterações com validação de justificativa):**
   **Dado** um usuário autenticado no detalhe de um PR,
   **quando** seleciona "Solicitar alterações",
   **então** a submissão é bloqueada localmente se o texto de justificativa estiver vazio; e quando preenchido e aceito pelo servidor (`200 OK`), o novo review com estado "Solicitou alterações" é adicionado à lista.

3. **REVIEW-SELF (Tratamento de auto-revisão):**
   **Dado** que o usuário autenticado é o próprio autor do PR ou o servidor devolve `422 Unprocessable Entity` ao tentar aprovar ou solicitar alterações,
   **quando** tenta aprovar ou solicitar alterações no seu próprio PR,
   **então** uma mensagem clara explicativa ("Você não pode aprovar ou solicitar alterações no seu próprio pull request.") é exibida, e o rascunho digitado é preservado.

4. **REVIEW-ANTI-DOUBLE-TAP (Proteção contra toques repetidos):**
   **Dado** que o envio de uma revisão está em andamento,
   **quando** o usuário aciona o botão repetidamente,
   **então** novos toques são ignorados, o botão permanece desabilitado com indicador de progresso e apenas uma requisição HTTP é emitida.

5. **MUTATION-GUARD (Preservação de rascunho em falha e bloqueio offline):**
   **Dado** erro de rede/timeout/403 ou aplicação em modo offline,
   **quando** o usuário tenta submeter a revisão ou a chamada falha,
   **então** o texto digitado permanece no formulário e, se em modo offline, nenhuma chamada de rede é emitida e o banner informativo é apresentado.
