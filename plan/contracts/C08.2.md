# C08.2 — Arquivos, diff e checks do pull request

## Escopo

No detalhe já existente do PR, exibir arquivos alterados com status, contagem
de adições/remoções e diff textual quando o GitHub fornecer `patch`. Os arquivos
são carregados em páginas explícitas; o patch de cada arquivo só é expandido
quando solicitado. Consultar checks (GitHub Checks API) e commit statuses
(Combined Status API) para o SHA do head validado do PR. Checks, arquivos e
diff são coleções somente leitura e independentes dos comentários e reviews de
C08.1.

Fora do escopo: comentários ancorados em linhas, abrir links remotos de arquivo
ou check, checkout local, executar workflows, escrever status/checks, editar,
comentar, aprovar ou mesclar PR. Não carregar conteúdo por `raw_url`,
`contents_url`, `html_url`, `details_url`, URL de check ou campos equivalentes.

## Pré-condições e decisões

- A tarefa depende de C08.1 e conserva sessão `repo`, cliente HTTPS restrito a
  `api.github.com`, cancelamento, limites de rate, Markdown inerte e tela de PR.
  Não ampliar escopos OAuth.
- `GET /repos/{owner}/{repo}/pulls/{number}` fornece `head.sha`; validar SHA
  hexadecimal de 40 caracteres e identidade do PR/repositório antes de usá-lo.
  Codificar o SHA como segmento da URL; não usar URLs retornadas no JSON.
- Arquivos: `GET /repos/{owner}/{repo}/pulls/{number}/files?per_page=100` e
  seguir somente `rel="next"` validado pelo cliente existente. O GitHub limita
  a resposta a 3.000 arquivos. Paginação ocorre somente por ação explícita,
  limitada a 30 páginas; se houver outro `next` ao atingir o teto, informar que
  a lista foi limitada pelo GitHub. Status, caminho e contagens são dados; não
  renderizar nomes como Markdown ou links.
- `patch` pode estar ausente, inclusive em arquivo binário ou quando o GitHub
  não fornece um trecho completo. A API não dá motivo confiável para distinguir
  esses casos. Mostrar “Diff não fornecido pelo GitHub (arquivo binário ou
  trecho indisponível/truncado)” para qualquer arquivo sem patch; nunca afirmar
  detecção específica de binário/truncamento. Mostrar patch como texto inerte,
  expandido sob ação do usuário e limitado a 20.000 caracteres por arquivo, com
  aviso de corte local se exceder esse limite.
- Checks: consultar
  `GET /repos/{owner}/{repo}/commits/{head.sha}/check-runs?filter=latest&per_page=100`
  e `GET /repos/{owner}/{repo}/commits/{head.sha}/status?per_page=100` em cargas
  independentes. Validar arrays, estados permitidos e SHA retornado quando
  presente. Checks e statuses usam estados/itens separados; não somar ou
  substituir um pelo outro. Nenhum item em ambos significa “Nenhum check ou
  status informado para este commit”, não sucesso. Traduzir queued/in_progress/
  completed e conclusões conhecidas; conclusão desconhecida permanece rotulada
  como indisponível. Os dois endpoints têm paginação REST; carregar página
  adicional apenas mediante ação explícita, com mesmo limite de 100 páginas/
número máximo de 10.000 itens.
- Checks em PRs de fork podem estar ausentes porque a Checks API procura pushes
  no repositório onde o check foi criado. Tratar lista vazia como “nenhum check
  informado neste repositório/commit” sem afirmar aprovação. Falha de uma fonte
  não apaga a outra.
- `401` expira sessão uma vez; rate limit, rede, `403`, `404`/`410`, `422`,
  `5xx`, JSON inválido e cancelamento recebem estados por seção e retry
  explícito. Erro em arquivos não apaga comentários/reviews; erro em checks não
  apaga arquivos/statuses. Não registrar tokens, patches reais ou caminhos
  privados em logs, fixtures versionadas ou evidências.

Fontes oficiais: [List pull request files](https://docs.github.com/en/rest/pulls/pulls#list-pull-requests-files),
[Get a pull request](https://docs.github.com/en/rest/pulls/pulls#get-a-pull-request),
[List check runs for a Git reference](https://docs.github.com/en/rest/checks/runs#list-check-runs-for-a-git-reference),
[Get the combined status for a specific reference](https://docs.github.com/en/rest/commits/statuses#get-the-combined-status-for-a-specific-reference) e
[REST API pagination](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api).

## Aceite

1. Dado PR carregado em C08.1, quando o detalhe termina de carregar, então
   arquivos, checks e statuses começam em cargas independentes e usam somente
   o repositório, número e head SHA validados daquele PR.
2. Dada resposta de arquivos em mais de uma página, quando “Carregar mais
   arquivos” é acionado, então segue apenas `rel="next"`, anexa sem duplicar,
   mantém a página atual em erro e oferece retry; ao atingir 3.000 itens/30
   páginas, informa limite e remove continuação.
3. Dado arquivo com patch, quando a pessoa expande o arquivo, então vê diff
   textual inerte com status e contagens; patch vazio ou ausente mostra a
   mensagem de diff não fornecido. Patch acima de 20.000 caracteres é cortado
   localmente e identificado como corte local.
4. Dado muitos arquivos ou patches longos, quando a tela abre ou rola, então
   somente uma página limitada é buscada, nenhum patch é expandido
   automaticamente, e a UI continua responsiva.
5. Dadas respostas de check runs e statuses, quando válidas, então estados
   pendentes, em andamento, sucesso, falha e conclusão desconhecida são
   representados separadamente. Listas vazias nunca são mostradas como sucesso.
6. Dada falha/limite/JSON inválido/cancelamento numa fonte, quando ocorre, então
   só a seção afetada mostra erro, com retry quando aplicável; outras coleções
   do PR e respostas já carregadas são preservadas. Voltar ou trocar PR cancela
   cargas antigas, e resposta de outro PR/sessão nunca aparece.
7. Dado PR cujo head está em fork ou cujo check/status não pode ser acessado,
   quando a fonte retorna vazio ou erro, então a UI informa ausência/falha sem
   inferir sucesso e sem ocultar arquivos ou a fonte independente.
8. Dado uso somente leitura, quando o fluxo e as requisições são testados,
   então nenhum método ou rota de mutação é usado; os diffs, caminhos e textos
   não carregam links nem conteúdo remoto.
