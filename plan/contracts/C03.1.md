# C03.1 — Autorizar conta GitHub

## Escopo

Implementar o Device Flow do OAuth App configurado em C02.1: solicitar código,
mostrar código de usuário e endereço oficial, abrir esse endereço, respeitar o
intervalo/expiração durante polling, buscar `GET /user` com o token e mostrar o
perfil real somente após sucesso. Permitir cancelar e tentar novamente. Token e
estado de sessão ficam apenas em memória nesta entrega; persistência, renovação,
logout e limpeza de cache pertencem a C03.2. O modo demonstração permanece
claramente separado.

## Pré-condições e decisões

- C01.1 e C02.1 concluídos; Client ID público pode estar ausente no build.
- Solicitar os escopos documentados em `docs/AUTH.md`. Usar os endpoints HTTPS
  oficiais `github.com/login/device/code` e `github.com/login/oauth/access_token`
  usando os corpos form-encoded padrão documentados pelo GitHub. Buscar perfil
  em `api.github.com/user` pelo cliente REST existente; não enfraquecer sua
  restrição de origem.
- Respeitar `interval`; `authorization_pending` mantém polling e `slow_down`
  acrescenta ao menos cinco segundos. Expiração, negação, cancelamento, erro de
  rede, configuração ausente e falha ao buscar perfil não criam sessão.
- Usar transporte separado para os POST OAuth. Não registrar códigos, tokens,
  corpos OAuth nem dados privados. Não guardar token após recriação do processo.
- Manter a decisão atual por Device Flow e o risco documentado em `docs/AUTH.md`;
  não migrar para PKCE/GitHub App dentro desta entrega.
- Testes do fluxo usam servidor local controlado. Aceite real requer que o
  proprietário autorize uma solicitação iniciada no app, sem registrar ou
  capturar código/token; não usar uma solicitação real sem a participação dele.

## Aceite

1. Dado Client ID ausente, ao tentar conectar, o app informa que a configuração
   está indisponível e continua sem sessão autenticada.
2. Dado um Device Flow iniciado, o app mostra código copiável e link oficial;
   abrir o link não interrompe polling, e cancelar interrompe chamadas futuras.
3. Dado `authorization_pending`, o cliente aguarda o intervalo informado antes
   do próximo POST; dado `slow_down`, aumenta o intervalo em pelo menos cinco
   segundos. Nenhum POST excede a frequência permitida.
4. Dada autorização negada, código expirado, erro HTTP/rede ou perfil inválido,
   o app volta ao estado sem sessão, apresenta erro seguro e permite tentar de
   novo.
5. Dada autorização válida, o app valida token com `GET /user` e mostra login e
   avatar/URL do perfil retornado. A demonstração continua identificada como
   fictícia e não é apresentada como sessão real.
6. Dado reinício do processo antes de C03.2, nenhuma sessão é restaurada e
   nenhum token é persistido. Rotação encerra o fluxo em andamento com segurança.
7. Na autorização real do proprietário, a conta exibida corresponde ao perfil
   retornado pelo GitHub; evidência não contém códigos, token ou captura com
   informações privadas.
