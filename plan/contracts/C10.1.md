# C10.1 — Workflows, execuções e jobs

## Escopo

No detalhe do repositório selecionado, oferecer uma área somente leitura de
GitHub Actions. Listar workflows, execuções recentes por workflow ou todas as
execuções recentes do repositório; abrir uma execução e listar seus jobs com
status e conclusão. Atualização e paginação são explícitas. Reutilizar sessão,
transporte HTTPS restrito à API GitHub e proteção de expiração existentes.

Não incluir logs, disparar, cancelar ou reexecutar workflows, artefatos,
cache/offline, filtros avançados ou persistência. Logs pertencem a C10.2.

## Pré-condições e decisões

- C06.1 fornece a identidade estável do repositório e navegação pelo detalhe;
  C03.2/C04.1/C04.2 fornecem sessão, cliente REST e paginação validada.
- Usar `GET /repos/{owner}/{repo}/actions/workflows?per_page=50`,
  `GET /repos/{owner}/{repo}/actions/runs?per_page=50`,
  `GET /repos/{owner}/{repo}/actions/workflows/{workflow_id}/runs?per_page=50`
  e `GET /repos/{owner}/{repo}/actions/runs/{run_id}/jobs?filter=latest&per_page=50`.
  Seguir somente `Link rel="next"` validado pelo transporte existente e carregar
  no máximo uma página por ação do usuário.
- A documentação REST oficial confirma que OAuth App tokens precisam de
  `repo` para workflows, runs e jobs em repositórios privados. O OAuth Device
  Flow do app já solicita `repo`; não ampliar nem trocar escopos nesta tarefa.
  Permissões da conta, organização e disponibilidade de Actions continuam
  limitando respostas.
- Construir caminhos a partir de `owner`/`name` do `GitHubRepository` e IDs
  numéricos positivos validados. Não seguir URLs `url`, `html_url`, `jobs_url`
  ou quaisquer links do corpo JSON.
- Mapear estado de workflow, run e job por códigos conhecidos em português;
  valores desconhecidos recebem rótulo neutro preservando o valor sanitizado.
  Run/job sem `conclusion` (ainda não concluído) é apresentado como “Em
  andamento”/“Aguardando conclusão”, nunca como sucesso. `completed` com
  conclusão ausente é estado não classificado, apresentado como “Conclusão não
  informada”, não sucesso.
- `200` vazio é vazio real. `401` encerra a sessão por callback existente;
  `403`, `404`, rede, rate limit, `5xx` e JSON malformado são erro visível com
  retry, nunca lista vazia. `404` não deve afirmar se repositório privado existe.
- Somente GETs; não usar endpoints de logs nesta entrega para manter a fronteira
  com C10.2. Não registrar token nem conteúdo de execução/job em logs.

Fontes oficiais: [endpoints REST de workflows](https://docs.github.com/en/rest/actions/workflows),
[endpoints REST de workflow runs](https://docs.github.com/en/rest/actions/workflow-runs?apiVersion=2022-11-28),
[endpoints REST de jobs](https://docs.github.com/en/rest/actions/workflow-jobs)
e [paginação REST](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api).

## Aceite

1. Dada sessão válida e repositório selecionado, quando a pessoa abre GitHub
   Actions, então workflows reais do mesmo repositório são exibidos; resposta
   vazia mostra estado vazio sem dados de demonstração.
2. Dado workflow habilitado ou desabilitado, quando exibido, então seu nome e
   estado correspondem à API; campos obrigatórios inválidos não são apresentados
   como workflow válido.
3. Dado workflow selecionado ou opção de todas as execuções, quando a lista abre,
   então cada execução pertence ao repositório consultado e apresenta workflow,
   branch, evento, data, status e conclusão disponíveis sem converter nulos em
   sucesso.
4. Dada execução selecionada, quando jobs carregam, então ID da execução e
   repositório correspondem à seleção; cada job mostra status/conclusão e valores
   desconhecidos usam fallback explícito.
5. Dada resposta paginada, quando Carregar mais é acionado, então só a próxima
   página same-origin validada é carregada, sem duplicatas; sem `rel="next"` não
   existe continuação.
6. Dada falha HTTP, rede, rate limit ou resposta inválida, quando exibida, então
   a UI não a confunde com lista vazia; retry explícito preserva dados já
   carregados e não repete páginas bem-sucedidas.
7. Dado `401`, quando o transporte detecta sessão expirada, então o callback
   encerra a sessão uma vez; `403` e `404` permanecem erros de recurso/permissão.
8. Dado o fluxo completo, quando tráfego e logs são inspecionados, então há
   somente GETs de workflows/runs/jobs; nenhum endpoint de escrita/logs ou token
   em logs é usado.
