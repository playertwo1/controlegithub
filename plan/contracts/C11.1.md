# C11.1 — Cache de leituras

## Escopo

Implementar persistência local e isolada de respostas de leitura da API do GitHub utilizando SQLite nativo do Android (`SQLiteOpenHelper`) sem novas dependências externas.
Permitir que o aplicativo, ao ser reiniciado sem conexão de rede ou quando uma consulta de leitura falhar por falta de conectividade, recupere e apresente a última representação válida salva dos recursos (repositórios, issues, pull requests, notificações), identificando a origem dos dados como offline e indicando o horário da captura.
Garantir o isolamento estrito dos dados por conta autenticada (`accountLogin`), prevenindo qualquer compartilhamento de cache entre contas distintas.
Exclusões deste contrato:
- Atualização forçada por pull-to-refresh com cabeçalhos de revalidação condicional HTTP (`If-None-Match`/ETag) e tratamento de `304 Not Modified` no refresh (pertencem a C11.2).
- Reenvio automático de requisições por listener de conectividade de rede (pertence a C11.2).
- Fila de escrita offline ou mutações em segundo plano (proibidas pelas regras do projeto).
- Cache de segredos, tokens OAuth, respostas de autenticação, logs de GitHub Actions ou URLs temporárias de download.

## Pré-condições e decisões

- Pré-requisitos C07.2, C08.2, C09.2 e C10.2 estão concluídos (`DONE`).
- Decisão sobre banco de dados: utilizar SQLite nativo (`android.database.sqlite.SQLiteOpenHelper`) armazenado no diretório privado da aplicação (`context.noBackupFilesDir` ou `context.filesDir`), sem adicionar bibliotecas externas de ORM (como Room ou GreenDAO), mantendo zero dependências adicionais e total controle sobre o ciclo de vida do arquivo.
- Decisão sobre chaveamento e isolamento: a chave primária do cache é composta por `(account_login, resource_key)`. O `account_login` é normalizado em minúsculas. Nenhum token, senha ou dado sensível entra na chave de recurso ou no nome do banco.
- Decisão sobre restauração de sessão offline: `SecureSessionStore` e `GitHubSessionManager` devem persistir o perfil básico verificado (`GitHubUser`: login e html_url) juntamente com as credenciais cifradas. Ao reiniciar o app sem rede, se o token local ainda for válido (não expirado pelo `accessExpiresAtMillis`), a sessão é restaurada no modo offline em vez de abortar com tela de erro de sessão, permitindo a navegação no cache local.
- Decisão sobre expiração e limpeza:
  - Cada entrada possui `created_at` e `expires_at` baseados em TTL configurável por tipo de recurso (padrão 24 horas para leituras).
  - Limite de armazenamento de segurança (máximo de 500 entradas ou 10 MB total).
  - Ao executar `logout`, todo o cache da conta correspondente é imediatamente e atomicamente deletado do banco de dados SQLite.

## Aceite

1. **CACHE-01 (Consulta offline com cache prévio):**
   **Dado** que o usuário autenticado carregou com sucesso uma lista de recursos (repositórios, issues, pull requests ou notificações),
   **quando** o aplicativo é reiniciado sem conexão de rede (ou a rede falha com erro de conexão),
   **então** a tela restaura a sessão localmente e exibe os itens previamente salvos no cache, apresentando indicador explícito de "Modo offline" com a data/hora da última sincronização válida.

2. **CACHE-02 (Consulta offline sem cache prévio):**
   **Dado** que uma consulta específica (ou filtro) nunca foi carregada previamente,
   **quando** o usuário tenta acessá-la sem conexão de rede,
   **então** a tela informa claramente a ausência de conexão e a inexistência de dados salvos em cache, sem exibir spinner infinito, dados de demonstração ou lista falsamente vazia.

3. **CACHE-03 (Isolamento estrito entre contas):**
   **Dado** que o usuário A autenticou e gerou entradas de cache no dispositivo,
   **quando** o usuário A realiza logout e o usuário B se conecta,
   **então** nenhum dado, lista ou detalhe pertencente ao usuário A é visível ou recuperado para o usuário B.

4. **CACHE-04 (Limpeza atômica no logout):**
   **Dado** que existem entradas no banco de cache para a conta conectada,
   **quando** o usuário conclui o fluxo de logout,
   **então** todas as entradas associadas àquela conta são removidas do SQLite.

5. **CACHE-05 (Resiliência contra corrupção e entradas inválidas):**
   **Dado** uma entrada de cache corrompida, com schema inválido ou expirada além do limite aceitável,
   **quando** o cache é consultado,
   **então** a entrada inválida é descartada com segurança, sem crash da aplicação e sem interrupção das demais entradas íntegras.

6. **CACHE-06 (Proteção de dados sensíveis):**
   **Dado** a gravação de qualquer dado no cache SQLite,
   **quando** os registros do banco são inspecionados,
   **então** verifica-se que nenhuma credencial (token OAuth, refresh token, client secret) ou log de execução de Actions foi gravado na base de cache.
