# C09.2 — Marcar uma notificação como lida

## Escopo

No detalhe de uma notificação não lida, oferecer uma ação explícita para marcá-la
como lida no GitHub. Atualizar o estado local somente após confirmação HTTP.
Não incluir marcar todas como lidas, marcar como concluída, ocultar, subscriptions
ou qualquer chamada `PUT /notifications`/`DELETE /notifications/threads/{id}`.

## Pré-condições e decisões

- C09.1 concluída; reutilizar a sessão OAuth Device Flow e o cliente HTTP restrito
  a `api.github.com` já existente.
- Usar `PATCH /notifications/threads/{thread_id}`. `thread_id` deve ser o ID
  numérico validado recebido na lista; não construir a rota a partir de URL da API.
- A referência REST oficial documenta `205` e `304` como respostas do endpoint,
  mas afirma que os endpoints de notificações aceitam somente PAT classic. A
  consulta `GET /notifications` com OAuth retornou `200` em C09.1, o que não
  comprova que este `PATCH` funciona com OAuth. Testar o token OAuth atual; se o
  GitHub negar, manter o resultado `BLOCKED` e pedir uma decisão separada antes
  de propor ou implementar outra autenticação.
- O proprietário autorizou uma tentativa real em exatamente uma notificação
  não lida para validar C09.2. Registrar apenas status HTTP e resultado visual;
  não salvar ID, título, repositório, URL, corpo ou token.
- Não tratar timeout/rede como sucesso. A requisição pode ter sido aplicada
  antes de a resposta se perder; manter estado local não confirmado e permitir
  nova tentativa idempotente para o mesmo thread.

Fonte oficial: [REST API — Mark a thread as read](https://docs.github.com/en/rest/activity/notifications?apiVersion=2022-11-28#mark-a-thread-as-read).

## Aceite

1. Dada uma notificação não lida aberta no detalhe, então há ação identificada
   “Marcar como lida”; notificações já lidas não oferecem essa ação.
2. Quando a ação é acionada, então envia somente um `PATCH` para
   `/notifications/threads/{id}` com o ID numérico da notificação e o token no
   cabeçalho; não envia corpo, URL arbitrária ou operação em lote.
3. Dada resposta `205` ou `304`, então o detalhe e a lista passam a mostrar
   “Lida” e a ação deixa de aparecer. Estado de leitura só muda após essa
   resposta confirmada.
4. Dada resposta `401`, então o callback compartilhado de sessão expirada é
   acionado. Dado `403`, então erro explícito informa que OAuth não foi aceito;
   não mostrar sucesso nem trocar para PAT.
5. Dada falha de rede, timeout, rate limit, `5xx` ou resposta inesperada, então
   a notificação permanece localmente não lida, o erro é visível e a pessoa pode
   tentar novamente.
6. Com fixture local, testar sucesso `205`/`304`, `401`, `403`, falha transitória,
   request method/path/cabeçalho e estado visual. Nenhum dado fictício é
   apresentado como dado real; a Activity de fixture continua restrita a debug.
7. No Pixel 9/API 37, executar a ação uma vez sobre uma notificação real não
   lida autorizada pelo proprietário. Registrar status HTTP e estado visual;
   validar a mudança no GitHub sem capturar conteúdo privado.
