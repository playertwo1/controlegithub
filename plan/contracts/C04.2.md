# C04.2 — paginação e espera por rate limit

## Escopo

Carregar uma página por chamada explícita, seguir somente `rel="next"` do
cabeçalho `Link`, preservar a ordem e remover itens repetidos pela chave estável
fornecida pelo consumidor. Rejeitar links fora da origem GitHub já validada por
C04.1 e parar ao detectar cursor repetido. Para 429 e 403 reconhecido como rate
limit, retornar prazo seguro de retry e bloquear novas chamadas pelo mesmo
cliente HTTP até esse prazo, inclusive em outros paginadores. Não iniciar retry
automático nem carregar todas as páginas em loop. Não decodificar JSON;
consumidor fornece decoder e chave do item.

## Pré-condições e decisões

- C04.1 DONE; seu transporte mantém `Link`, `Retry-After`,
  `X-RateLimit-Remaining` e `X-RateLimit-Reset`.
- O GitHub informa páginas pelo cabeçalho `Link`; URL e parâmetros variam por
  endpoint. Reutilizar a URL `next` inteira sem construir parâmetros `page`.
- 429 ou 403 com `Retry-After`/`X-RateLimit-Remaining=0` é tratado como rate
  limit. Esperar o maior prazo indicado por `Retry-After` e `X-RateLimit-Reset`;
  sem esses valores, usar 60 segundos conforme orientação oficial. O prazo é
  informativo/gating local; apenas ação explícita do consumidor envia novo GET.
- O cliente HTTP compartilha o bloqueio entre endpoints para evitar que outro
  paginador contorne o prazo. Injetar relógio no cliente para testar sem espera
  real. Sem biblioteca JSON nova; DTOs específicos e UI ficam nas tarefas de
  recurso.

## Aceite

1. Dadas duas páginas ligadas por `rel="next"` com itens repetidos, quando o
   consumidor carrega ambas, então recebe itens únicos na ordem da primeira
   ocorrência e pode continuar pela URL fornecida no header.
2. Dado link ausente, malformed ou cursor já visitado, quando carrega uma
   página, então encerra ou falha em estado seguro, mantém itens anteriores e
   não faz requisição adicional em ciclo.
3. Dado 429, 403 com `Retry-After`, ou 403 com `X-RateLimit-Remaining=0`, quando
   carrega a página, então recebe retryAt coerente com os headers; sem prazo
   utilizável, retryAt fica pelo menos 60 segundos no futuro.
4. Dada falha rate-limited antes de retryAt, quando qualquer paginador usa o
   mesmo cliente HTTP, então retorna o mesmo bloqueio sem consultar a rede.
   Após retryAt, uma chamada explícita pode repetir somente o GET pendente.
5. Dado link `next` para outra origem ou esquema inseguro, quando o consumidor
   carrega a página, então a origem é recusada antes de enviar Bearer.
6. Dada falha HTTP ou de rede, quando o consumidor recebe o resultado, então a
   mensagem é segura e itens previamente carregados permanecem disponíveis.
