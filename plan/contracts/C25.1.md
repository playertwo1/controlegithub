# C25.1 — Acessar repositórios a partir de Avisos e baixar APK

> Build this with **tlc-implement**. Cada critério vira uma verificação com prova. Não resolva `Unresolved` durante a implementação.

## Intent

Na tela Avisos, cartões de notificações de release e outros assuntos mostram o
repositório de origem, mas assuntos que o app não reconhece não têm destino de
navegação. A pessoa precisa sair da caixa e procurar o repositório manualmente;
isso também torna releases e APKs mais difíceis de alcançar.

O pedido é abrir o repositório apresentado no aviso, acessar as funções que já
existem no aplicativo e baixar um APK por Releases. A captura enviada mostra a
entrada Avisos, os filtros e cartões com nome do repositório e tipo do assunto;
ela não pede uma mudança visual.

1 slice · 0 one-way doors · 2 open, 0 blocking.

## Escopo

- Preservar os destinos atuais de notificações `Issue` e `PullRequest`.
- Para `Repository`, assunto ausente ou assunto desconhecido/“Outro”, habilitar
  a abertura do detalhe do repositório quando `repositoryId` e `full_name` forem
  válidos. Não seguir `subject.url` nem outra URL arbitrária para esse fallback.
- A partir do detalhe, reutilizar resumo/README, Código, GitHub Actions e
  Releases/APKs já implementados. A ação existente “Nova issue” permanece
  sujeita à permissão atual do GitHub. Selecionar um APK usa o fluxo C21.2 de
  download e instalação manual.
- Resolver repositórios pelos dados da notificação; não codificar os nomes da
  captura.
- Manter a caixa, filtros, página e posição da lista ao voltar.

## Pré-condições e decisões

- C09.1, C21.1, C21.2 e C24.1 estão `DONE`. C21.3 é a validação física separada
  e continua `PLANNED`/`NOT_RUN`; por decisão do proprietário, não é dependência
  de C25.1 nem gate para fechar o checkpoint C25. C25.1 depende diretamente de
  C21.2, tarefa já concluída, sem depender do fechamento do checkpoint C21.
- `notificationDestination` em `GitHubNotifications.kt` atualmente retorna
  `Unavailable` para tipos diferentes de Issue/PullRequest/Repository. A tela
  desabilita “Abrir item de origem” nesse caso.
- `GitHubRepositoryDetailScreen` já mostra dados/README e fornece Código,
  Actions, Nova issue e Releases/APKs. Releases e download usam C21.1/C21.2;
  C21.2 valida SHA-256 e exige ação manual para abrir o instalador.
- Usar a conta e o token OAuth já ativos. Não adicionar escopos, PAT ou segredo.
  Repositório privado só abre se a conta autorizada tiver acesso; respostas de
  acesso negado continuam explícitas.
- Até resposta do proprietário, “acessar tudo” significa alcançar as funções
  que o aplicativo já oferece para o repositório, dentro das permissões da
  sessão. Não implica espelhar todos os endpoints nem criar novas ações.

## Criteria

### Aviso com origem de repositório

1. Dada uma notificação `Issue` ou `PullRequest` válida, quando abro sua origem,
   então o destino específico atual continua abrindo o detalhe correto.
2. Dada uma notificação `Outro`, de `Release` ou com tipo desconhecido e uma
   identidade de repositório válida, quando escolho “Abrir item de origem”, então
   o detalhe mostra o `owner/repo` recebido no aviso e habilita suas funções
   atuais. A rota não usa uma lista fixa de repositórios nem segue URL do assunto.
3. Dado nome/ID inválido ou repositório inacessível, quando tento abrir a origem,
   então vejo indisponibilidade/erro explícito; não aparece detalhe fictício nem
   a falha é convertida em estado vazio.

### Acesso e download de release

4. Dado o repositório aberto a partir de Avisos, quando navego pelo detalhe,
   então posso abrir seus dados/README, Código, Actions, Releases e a ação
   existente Nova issue; cada tela continua consultando o repositório
   selecionado, e ações de escrita continuam sujeitas às permissões atuais.
5. Dada uma release com APK, quando seleciono o asset, então C21.2 apresenta o
   andamento e o resultado de SHA-256 e só abre o instalador após toque explícito
   do usuário. Se não houver APK, vejo o estado existente “nenhum APK disponível”.
6. Quando volto do detalhe do repositório e depois da notificação, então retorno
   à lista com filtros, páginas carregadas e posição preservados.
7. Dado um detalhe aberto a partir de Avisos, quando TalkBack foca o botão
   Voltar, então o rótulo acessível indica “Voltar à notificação”; quando o
   detalhe foi aberto pela lista Repositórios, o rótulo existente “Voltar aos
   repositórios” permanece correto.

## Aceite

Ver os critérios 1–7 acima; eles são a fonte única dos cenários de aceite.

## Out of scope

- Criar listas de issues ou pull requests filtradas por repositório; já existem
  destinos de notificação para itens individuais e a área Trabalho continua
  sendo a lista geral. Isso fica pendente da resposta em `Unresolved`.
- Criar/editar arquivos, branch, commit, push, merge, administrar repositórios,
  adicionar ações de escrita que ainda não existem, ampliar escopos OAuth ou
  adicionar outro método de autenticação.
- Baixar APK automaticamente, instalar sem confirmação, baixar artefatos que
  não sejam APK ou alterar a política de checksum de C21.2.
- Alterar o layout da tela Avisos ou dos detalhes já aprovados.

## Swept

- validation: 2, identidade `repositoryId`/`full_name` validada; nenhuma URL arbitrária.
- failure modes: 3, repositório inválido/inacessível e falha explícita.
- idempotency and retry: existing — detalhe/release mantêm retry atual; C21.2 usa trabalho único por repositório e asset.
- authorization: existing — sessão OAuth e permissões atuais; sem novo escopo.
- concurrency and ordering: 5, download já deduplica pelo par repositório/asset; voltar não reinicia a lista.
- data lifecycle: n/a — sem novos dados persistidos; download obedece ao ciclo e destino de C21.2.
- external-dependency failure: 3, erros HTTP/rede e acesso negado permanecem visíveis.
- state transitions: 1, 2, 4, 5, 6, 7 — aviso → detalhe de origem → detalhe do repositório → telas existentes → volta com rótulo contextual.
- observability: 3, 5 — feedback visível no app; não registrar token, URL de download ou conteúdo privado.
